## 00 · Notice to Navigation

**N.O.I.S.E. Chartroom** is an operational field console for systems governance, architecture, security, evidence and accountable execution.

It is designed to answer a small set of questions before work proceeds:

- **Who has authority?**
- **What is inside the boundary?**
- **What is explicitly outside it?**
- **What evidence supports the current state?**
- **What intervention is justified?**
- **Who owns the next action?**
- **What observable condition ends the work?**

The governing flow is intentionally simple:

```text
SIGNAL → BOUNDARY → AUTHORITY → ACTION → EVIDENCE → EXIT
```

Chartroom exists to convert ambiguous work into a **bounded, reviewable and finishable mandate**.

## 02 · Purpose

Chartroom is not a passive dashboard.

It is an **operational decision surface** for establishing whether a system, project or intervention is sufficiently defined to proceed.

### Core questions

| Signal | Question | Required outcome |
|---|---|---|
| **Authority** | Who may decide? | Named decision authority |
| **Boundary** | What may be touched? | Explicit inclusions and exclusions |
| **Evidence** | What is actually known? | Observable facts separated from inference |
| **Ownership** | Who executes? | Named accountable operator |
| **Exit** | What does finished mean? | Observable stop condition |
| **Depth** | How intrusive may the intervention become? | Classified intervention level |

A weak signal does not produce decoration.

It produces a review.

## 03 · Operating Doctrine

> **No mandate without boundary.**  
> **No boundary without authority.**  
> **No authority without evidence.**  
> **No execution without an exit condition.**

Chartroom is intentionally hostile to:

- undefined ownership,
- undocumented assumptions,
- invisible scope expansion,
- governance by implication,
- permanent "work in progress",
- status reporting without evidence,
- completion without an acceptance condition.

## 05 · Protocol Registry

### `BR-01` · Boundary Review

**Trigger:** authority, ownership, scope or escalation is ambiguous.

**Objective:** establish where authority begins, where it ends and what remains explicitly excluded.

**Required output:** a named authority boundary with inclusions, exclusions and escalation points.

---

### `RA-02` · Readiness Assessment

**Trigger:** implementation, migration or intervention is proposed without a stable operational picture.

**Objective:** determine whether the system is sufficiently understood to proceed.

**Required output:** readiness score, weak signals and a recommended next protocol.

---

### `MD-03` · Mandate Definition

**Trigger:** work exists without a finite owner, scope or exit condition.

**Objective:** convert intent into an executable mandate.

**Required output:** owner, scope, exclusions, review point, intervention depth and exit condition.

---

### `EV-04` · Evidence Check

**Trigger:** assumptions are being treated as facts.

**Objective:** separate evidence states.

**Required output:**

| State | Meaning |
|---|---|
| **Observed** | Directly verified |
| **Inferred** | Reasonable interpretation of observed evidence |
| **Unverified** | Claimed but not independently confirmed |
| **Contradicted** | Evidence exists against the claim |

---

### `EX-05` · Exit Review

**Trigger:** work persists after useful completion or lacks a defensible stop condition.

**Objective:** decide whether to close, hand over, escalate or continue.

**Required output:** documented exit decision and evidence supporting it.

---

## 06 · System Depth Classification

| Class | Designation | Scope |
|---|---|---|
| **I** | Light Draft | Low-risk clarification, bounded documentation or advisory output |
| **II** | Structured Review | Multi-signal analysis with explicit owner and scope |
| **III** | Operational Intervention | Active changes to process, configuration or architecture |
| **IV** | Controlled Reconstruction | Material redesign requiring evidence, rollback and review |
| **V** | Harbour Action ⚜️ | Reserved for conditions where pretending everything is fine has become operationally expensive |

### Depth rule

An intervention must not silently increase its depth class.

If execution crosses into a higher class, the mandate must be reviewed before continuing.

## 09 · Acceptance Test

A feature is not complete because it renders.

A protocol is not complete because it exists.

A mandate is not complete because it was written.

Completion requires **observable evidence** that the intended operational state has been reached.

### Minimum acceptance conditions

- [ ] authority is named
- [ ] scope is bounded
- [ ] exclusions are explicit
- [ ] evidence is distinguishable from assumption
- [ ] owner is accountable
- [ ] next action is finite
- [ ] exit condition is observable
- [ ] result can be communicated outside the console
- [x] lilies are present where structurally required ⚜️

## 10 · Contribution Protocol

Contributions are welcome when they improve:

- clarity,
- operational usefulness,
- evidence quality,
- maintainability,
- bounded execution,
- reviewability.

### Before opening a pull request

1. identify the operational problem,
2. state the authority boundary,
3. describe the proposed intervention,
4. provide acceptance evidence,
5. define what **done** means.

A pull request without an exit condition may remain at anchor.

docs: define exit review protocol

## 14 · Engineering Principles

### Prefer explicit over implied

If a boundary matters, write it.

If an authority matters, name it.

If evidence matters, classify it.

If completion matters, define it.

### Prefer finite over permanent

Every intervention should have:

- a start,
- an owner,
- a scope,
- a review point,
- an exit.

### Prefer evidence over confidence

Confidence is not an evidence state.

### Prefer boring infrastructure over decorative complexity

The system should remain understandable when:

- the original author is absent,
- the interface is unavailable,
- the project changes hands,
- a decision is challenged,
- a result must be audited.

## 15 · Failure Conditions

Chartroom should treat the following as operational defects:

| Condition | Response |
|---|---|
| No named authority | Stop and perform `BR-01` |
| Scope expands silently | Review mandate |
| Evidence cannot be classified | Perform `EV-04` |
| Owner is ambiguous | Block execution |
| Exit condition is missing | Mandate invalid |
| Intervention depth increases | Reauthorize |
| Status says "done" without evidence | Reject completion |
| Lilies missing | Immediate ceremonial remediation ⚜️ |
